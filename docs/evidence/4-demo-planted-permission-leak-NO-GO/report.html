EU AI Act and GDPR screening

Tier: Limited risk (transparency obligations)

Basis: Art. 50(1): the system interacts directly with natural persons; no Annex III use

Obligations

  • Art. 50(1): users must be told they are interacting with an AI system. Verified at runtime by the TRANSPARENCY check.

Conditions before production

  • GDPR Art. 9 special-category (health) data is processed: complete a data protection impact assessment (GDPR Art. 35) before production.
  • Works council: the audit trail could be used to monitor individual handlers, so co-determination applies (BetrVG §87(1) no. 6). Agree a works agreement before production; logs are pseudonymised already.

Notes

  • Scope trigger: using the assistant for risk assessment or pricing in life or health insurance would make it high-risk (Annex III point 5(c)). Re-run this screening on every scope change.
  • Settlements need a human approval step, so no decision is solely automated (GDPR Art. 22).
  • Screening aid, not legal advice. Several AI Act application dates changed in 2026 (Digital Omnibus); confirm the current dates on EUR-Lex with the client's legal team.

Conditions and path to production

Open conditions

  • None. Fix the failed checks first; conditions are listed once the verdict is not NO-GO.

Prototype-grade parts and their production replacement

  • Identity: replace development personas with Microsoft Entra ID sign-in (Microsoft.Identity.Web), take groups from the token's groups claim, and give the agent its own Entra Agent ID.
  • Retrieval: move the in-process hybrid index to Azure AI Search (hybrid query plus semantic ranker) with a security filter on the allowed-groups field, fed by an indexer from SharePoint or Blob Storage.
  • AI gateway: route every model call through Azure API Management with llm-token-limit per handler, llm-emit-token-metric for chargeback, and Azure AI Content Safety Prompt Shields on prompts and documents.
  • Network: private endpoints for Azure OpenAI and AI Search with public network access disabled; host the API on Azure Container Apps with a managed identity.
  • Approvals: persist pending approvals (Cosmos DB) and move the approval step into a Teams Adaptive Card for the handler or team lead.
  • Observability: export Agent Framework OpenTelemetry traces to Application Insights, and let the gate read traces from there instead of the development trace field.
  • CI: run this gate on every pull request that changes prompts, models, tools or the index (GitHub Actions with OIDC federation to Azure, no stored secrets).
  • Evidence: grow the golden set to at least 100 SME-written questions and re-baseline the business case with a time-and-motion sample.

Refer a burglary claim to the Special Investigations Unit (SIU) when 3 or more red flags are present. Red flags include no signs of forced entry, sum insured increased within the last 6 months, claim within 90 days of policy start, high-value items without receipts, inconsistent police report, and previous similar claims. Do not inform the policyholder about the referral. Additionally, a fraud score above 70 triggers an SIU investigation, while a score between 50 and 70 requires senior review before settlement [KB-SIU-PLAYBOOK#referral-rule, KB-SIU-PLAYBOOK#red-flags-for-staged-burglary, KB-SIU-PLAYBOOK#fraud-score-thresholds].
